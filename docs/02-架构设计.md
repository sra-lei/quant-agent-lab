# 02 · 架构设计

> 版本 v0.1 ｜ 对应需求 [01-需求文档.md](01-需求文档.md)

## 1. 设计原则

1. **Agent 之间零直接依赖**——只通过契约（Pydantic 模型 / JSON）通信，禁止 A 调 B 的内部方法
2. **业务逻辑与框架解耦**——编排用 LangGraph，但 Agent 是普通 Python 类，删掉 LangGraph 也能跑
3. **一切结论可追溯**——每个输出必带 `source`（数据从哪来）、`as_of`（什么时点）、`run_id`（哪次运行）
4. **失败可见**——宁可输出"数据缺失"，不输出"看起来合理"的假数据
5. **默认零成本可跑**——Mock 数据源让任何人 clone 即可运行

## 2. 分层

```
┌─────────────────────────────────────────────────────┐
│  Presentation    React + AntD + TanStack Query       │
├─────────────────────────────────────────────────────┤
│  API             FastAPI（REST + OpenAPI 自动文档）  │
├─────────────────────────────────────────────────────┤
│  Orchestration   Orchestrator 接口                   │
│                  ├─ SimpleOrchestrator（状态机，默认）│
│                  └─ LangGraphOrchestrator（可选）     │
├─────────────────────────────────────────────────────┤
│  Agent           5 个 Agent，统一 BaseAgent 生命周期  │
├─────────────────────────────────────────────────────┤
│  Domain          契约模型、策略、评分逻辑             │
├─────────────────────────────────────────────────────┤
│  Data            DataProvider 抽象 + 多源适配器       │
├─────────────────────────────────────────────────────┤
│  Persistence     SQLAlchemy 2.0 + SQLite/Postgres    │
└─────────────────────────────────────────────────────┘
```

**依赖方向严格向下**。上层可依赖下层，反之禁止。Agent 不感知 HTTP、不感知数据库实现。

## 3. 核心数据流

### 3.1 一次日度运行（`DailyResearchRun`）

```
POST /api/runs {goal, capital, risk, universe}
        │
        ▼
① Planner.plan()  ──► TaskPlan{DAG}
        │
        ▼
② Orchestrator 按 DAG 调度
        │
        ├─► Collector.collect(universe, date) ──► MarketSnapshot
        │        │
        │        ├─► ValueAnalyst.analyze(snapshot, params) ──► AnalystView
        │        └─► MomentumAnalyst.analyze(snapshot, params) ──► AnalystView
        │
        ▼
③ Planner.synthesize([views]) ──► ResearchConclusion（含分歧标注）
        │
        ▼
④ 落库：run / snapshot / views / conclusion
        │
        ▼
⑤ 前端拉取 / 观察员次日读取快照
```

### 3.2 关键点

- **Collector 只跑一次**，两个分析师共享同一份 `MarketSnapshot`（保证"同口径"，这是上一次项目踩过的坑）
- **两个分析师并行**（无依赖），编排器可并发执行
- **Planner 的 synthesize 不取平均**：冲突时输出 `disagreements[]`，前端高亮

## 4. 编排层设计

### 4.1 接口

```python
class Orchestrator(Protocol):
    name: str
    def run(self, plan: TaskPlan, ctx: RunContext) -> RunResult: ...
```

### 4.2 两种实现

| 实现 | 说明 | 何时用 |
|---|---|---|
| `SimpleOrchestrator` | 手写拓扑排序 + 状态机，全部逻辑可见 | 默认；调试；依赖最小 |
| `LangGraphOrchestrator` | 状态图 + checkpoint + 可视化 | 需要断点续跑、复杂分支、图可视化 |

**切换方式**：`ORCHESTRATOR=simple|langgraph` 环境变量。

### 4.3 为什么保留 Simple 实现

不是"以防万一"，是两个具体理由：

1. **调试成本**：多 Agent 流程出问题时，读 500 行自己的代码比读框架抽象快
2. **依赖成本**：LangGraph 会带来 langchain-core 等一串依赖，2C2G 机器和 CI 都受影响

两者共享同一套契约和 Agent，所以答案永远可以对照验证。

## 5. Agent 生命周期

```python
class BaseAgent(ABC):
    name: str
    input_schema: type[BaseModel]
    output_schema: type[BaseModel]

    def invoke(self, payload: BaseModel, ctx: RunContext) -> BaseModel:
        # 1. 校验输入契约（不合法直接抛，不猜）
        # 2. 记录开始（run_id / agent / 输入摘要）
        # 3. 执行 _run()
        # 4. 校验输出契约
        # 5. 记录耗时 / token / 结果摘要
        # 6. 返回
```

**约束**：`_run()` 内的实现不得直接访问数据库或 HTTP，一切外部依赖通过 `ctx` 注入。这样 Agent 可单测。

## 6. 数据层设计

### 6.1 接口

```python
class DataProvider(Protocol):
    name: str
    def quotes(self, codes: list[str], start: date, end: date) -> list[Bar]: ...
    def fundamentals(self, codes: list[str], period: str) -> list[Fundamental]: ...
    def announcements(self, codes: list[str], days: int) -> list[Announcement]: ...
    def market_breadth(self, date: date) -> MarketBreadth: ...
```

### 6.2 适配器矩阵

| 适配器 | 传输 | 用途 | 依赖 |
|---|---|---|---|
| `MockProvider` | 内存 | 开发 / CI / 演示 | 无 |
| `TdxMcpProvider` | MCP over HTTP | 行情、K线、选股、公告 | 通达信 MCP 服务 |
| `WindMcpProvider` | MCP over HTTP | 基本面、宏观、跨市场 | 本机 WindPy + MCP |

### 6.3 数据质量守卫

入库前统一过 `DataGuard`：

- **新鲜度**：`as_of` 距今超过 N 个交易日 → 标记 `stale=true`
- **完整性**：关键字段缺失 → `null` + `missing_fields[]`，**禁止填 0**
- **异常值**：单日涨跌幅 > 20%（非 ST/新股）→ `anomaly=true` 并保留原因
- **口径**：同一次运行的所有 Agent 必须用同一个 `snapshot_id`

## 7. 数据库设计

```
runs            run_id, goal, status, started_at, finished_at, cost_tokens, error
snapshots       snapshot_id, run_id, as_of, source, payload(JSON), quality(JSON)
views           view_id, run_id, agent, snapshot_id, payload(JSON), created_at
conclusions     conclusion_id, run_id, payload(JSON), disagreements(JSON)
reviews         review_id, period, payload(JSON), created_at
strategies      strategy_id, name, kind, params(JSON), enabled, created_at
agent_traces    trace_id, run_id, agent, step, input_digest, output_digest, ms, tokens
```

**为什么 payload 用 JSON**：Agent 契约会频繁演进，宽表会天天改 schema。可检索的字段才提列，其余存 JSON。

## 9. 可观测性与成本

- **运行轨迹**：每个 Agent 的输入摘要（前 500 字符）+ 输出全文 + 耗时 + token
- **成本闸门**：`MAX_TOKENS_PER_RUN` 超限直接中止，记录 `aborted_reason`
- **模型分级**：`cheap_model`（收集/格式化）、`strong_model`（分析师判断），配置可调
- **日志**：结构化 JSON，密钥自动脱敏

## 10. 部署形态

### 形态 A：全本地（推荐起步）
```
Windows PC：Wind 终端 + WindPy MCP  ┐
            通达信 MCP              ├─► 本机 FastAPI + SQLite + 前端
```
优点：Wind 依赖天然满足；缺点：不常开。

### 形态 B：混合（云上跑，本机供数）
```
云 ECS：FastAPI + 前端 + SQLite     ← 公网/隧道 ── 本机：Wind MCP
```
注意：Wind 密钥不出本机；MCP 走隧道（frp / cloudflared），仅白名单 IP。

### 形态 C：纯云（无 Wind）
通达信 MCP + Mock 兜底，基本面用公开财报接口替代。适合开源用户。

## 11. 扩展点

| 想加什么 | 怎么做 |
|---|---|
| 新数据源 | 实现 `DataProvider`，注册到 `data/registry.py` |
| 新分析师（如宏观/量化因子） | 继承 `BaseAgent`，在 `agents/registry.py` 注册，Planner 计划里引用 |
| 换编排框架 | 实现 `Orchestrator`，改 `ORCHESTRATOR` 环境变量 |
| 换存储 | 改 `db/session.py` 的连接串（SQLite → Postgres） |
| 加回测 | 新增 `backtest/` 模块，复用 `snapshots` 与 `views` 历史 |
