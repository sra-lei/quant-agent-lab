# ADR-001 · 编排层选型：LangGraph + 可替换接口

- 状态：**已接受**
- 日期：2026-11-13
- 决策者：项目发起人

## 背景

项目需要编排 5 个 Agent：规划官、收集员、价投专家、游资专家、观察员。核心问题是"谁决定下一步谁干活"。

三个候选：

| 方案 | 本质 | 代码量 | 可控性 | 学习价值 |
|---|---|---|---|---|
| 自研状态机 | 拓扑排序 + 任务状态 | 500–800 行 | 全部可见 | 低 |
| **LangGraph** | 状态图（节点/边/状态） | 依赖框架，业务代码少 | 中（框架抽象） | **高** |
| CrewAI | 角色扮演式团队 | 最少 | 低（黑盒） | 中 |

## 决策

**编排实现用 LangGraph，但在其上包一层自有 `Orchestrator` 接口。**

```python
class Orchestrator(Protocol):
    name: str
    def run(self, plan: TaskPlan, ctx: RunContext) -> RunResult: ...
```

- 默认实现：`SimpleOrchestrator`（自研，零重依赖，保证 2C2G 与 CI 可跑）
- 可选实现：`LangGraphOrchestrator`（`ORCHESTRATOR=langgraph` 切换）
- **Agent 与契约完全框架无关**：Agent 是普通 Python 类，删掉 LangGraph 也能运行

## 理由

1. **学习目标是明确的需求**：项目发起人希望借这个工程掌握 LangGraph。这是真实需求，不是理由包装。
2. **LangGraph 解决的是真问题**：状态持久化、断点续跑、条件分支、图可视化。这些自己写要几百行且容易错。
3. **但"框架无关的业务层"是必须的**：
   - 框架版本升级会带来破坏性变更，业务代码不能被绑死
   - 多 Agent 流程出问题时，能对照自研实现验证行为，是最好的调试手段
4. **成本可控**：LangGraph 的依赖只在编排层引入，数据层与 Agent 层不受影响。

## 被否决的方案

**纯自研**：能跑，但放弃了一个明确的工程学习机会；且 checkpoint、可视化要自己造轮子。

**CrewAI**：抽象层太厚，5 个 Agent 各有严格契约（尤其是"分歧必须显式标注"），角色扮演式框架很难表达这种约束。调试基本靠猜。

## 后果

### 正面
- 获得状态图、检查点、可视化能力
- 契约层独立，未来换框架成本低
- 两种实现可互为对照，便于验证

### 负面
- 依赖体积增加（langchain-core 等），2C2G 机器需实测；因此保留 Simple 实现作为轻量路径
- 需要学习框架概念（State、Node、Edge、Reducer），前期有学习曲线
- 框架抽象可能"泄漏"——复杂分支仍需写自己的状态判断逻辑

### 缓解
- CI 只用 Simple 实现跑全链路，避免测试被框架版本波动影响
- 契约测试（`tests/test_contracts.py`）与框架无关，任何实现都必须通过

## 复查条件

出现以下任一情况时重新评估本决策：

1. LangGraph 依赖导致部署目标机器内存不足
2. 框架升级连续两次引入破坏性变更
3. 编排逻辑简单到 Simple 实现已足够，LangGraph 的收益无法证明
