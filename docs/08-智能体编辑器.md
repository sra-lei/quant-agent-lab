# 08 · 智能体编辑器

> 前端 `/agents` 页面：新建与编辑智能体，包含名称、角色描述、工作流、可用工具、输出格式。

## 1. 配置模型

| 字段 | 类型 | 说明 |
|---|---|---|
| `agent_id` | string | 主键。内置为固定值（如 `value_analyst`），自定义为 `custom_<hash>` |
| `name` | string | 展示名，≤80 字 |
| `role` | text | **角色描述**：身份、职责、边界，会作为系统提示词的主体 |
| `workflow` | `[{name, instruction}]` | **工作流**：有序步骤，每步一句可执行指令 |
| `tools` | `string[]` | **可用工具**：必须来自工具注册表 |
| `output_format` | `{type, schema?}` | **输出格式**：`json_schema` / `markdown_table` / `text` |
| `enabled` | bool | 停用后不参与未来的流程编排 |
| `builtin` | bool | 系统预置，可编辑不可删除 |

## 2. 三条设计约束

### 2.1 工具必须来自注册表
不允许自由填字符串。填了不存在的工具，运行时才炸——这种错误不该留到运行阶段。
注册表在 `backend/app/agents/tools.py`，新增工具加一条即可，前端下拉框自动出现。

### 2.2 内置智能体可编辑但不可删
`builtin=true` 的条目（收集员/价投/游资/规划官/观察员）可以被改提示词、加步骤、换工具，
但不允许删除，`agent_id` 也不允许改——否则编排计划里的引用会断。

### 2.3 保存前可试运行
编辑器右上角「试运行」会真正执行一遍：

```
配置 → 拼装提示词（角色 + 工作流 + 工具 + 输出要求 + 输入）
     → LLM 生成
     → 按 output_format 校验
     → 返回结果与校验状态
```

**没有配置 LLM Key 时**：返回按 schema 生成的结构样例，并明确标记 `mock: true`，
前端显示黄色提示条。不会假装那是真实推理结果。

## 3. API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/agents/meta` | 工具清单、输出格式预设、默认 schema |
| GET | `/api/agents` | 列出全部智能体 |
| GET | `/api/agents/{id}` | 单个详情 |
| POST | `/api/agents` | 新建（自动生成 id） |
| PUT | `/api/agents/{id}` | 全量更新 |
| DELETE | `/api/agents/{id}` | 删除（内置返回 400） |
| POST | `/api/agents/{id}/run` | 试运行，body: `{"input": {...}}` |

## 4. 输出格式与校验

`json_schema` 模式使用**自带的极简校验器**（`config_agent._validate`），支持：

`type` / `required` / `properties` / `items` / `enum` / `minimum` / `maximum`

**为什么不引入 jsonschema 库**：开源用户不该为了一个校验器多装一个依赖，
而以上关键字已覆盖本项目全部用例。需要完整 JSON Schema 时可替换实现，
校验函数的签名保持不变。

## 5. 工具：从声明到执行

早期版本里「可用工具」只是拼进提示词的文字。现在它是**真的会被调用**的。

### 5.1 三段结构

```
tools.py          声明：key / 文案 / args_schema（JSON Schema）
      ↓
tool_handlers.py  实现：同名 handler(ctx, args) -> dict
      ↓
config_agent.py   执行循环：模型要工具 → 执行 → 结果回灌 → 再问模型
```

三段用同一个 key 对齐，声明里没有的工具在执行阶段直接拒绝。

### 5.2 执行循环

```
轮次 1：模型返回 tool_calls（可能多个）
        → 逐个执行（校验是否在该 Agent 的 tools 白名单里）
        → 结果以 JSON 追加到对话
轮次 2：模型看到结果，给出最终答案
（最多 4 轮，防死循环）
```

模型若请求了**不在白名单里的工具**，直接拒绝并告诉它原因——不能靠模型自觉。

### 5.3 八个工具的实际作用

| 工具 | 实际做什么 | 数据来源 |
|---|---|---|
| `market.quotes` | 取日线，返回最近 10 根 + 最新收盘 | `DataProvider.quotes` |
| `market.fundamentals` | 取 PE/PB/ROE/同比 | `DataProvider.fundamentals` |
| `market.announcements` | 取近 N 天公告 | `DataProvider.announcements` |
| `market.breadth` | 涨跌家数、涨停数、换手 | `DataProvider.market_breadth` |
| `calc.indicators` | MA5/10/20、5/20 日涨跌、量比 | 拉行情后本地计算 |
| `calc.score` | 估值 40% + ROE 30% + 成长 30% | 本地规则，可复算 |
| `llm.complete` | 让模型针对子问题再答一次 | LLM 抽象层 |
| `report.write` | 写 Markdown 报告到 `reports/` | 本地文件系统 |

### 5.4 三条实现约束

1. **工具失败不抛异常**——返回 `{"error": ...}`，让模型自己决定是重试、换参数还是明说拿不到
2. **返回值必须裁剪**——行情只回最近 10 根，否则一次调用就能把上下文撑爆
3. **全部走 `DataProvider`**——不直连网络，所以 mock 模式下工具同样能跑通

### 5.5 试运行里能看到什么

前端试运行会显示：**工具调用次数 / 轮次 / 每次调用的参数与返回**。
即使没有 LLM Key，工具也是真实执行的（取的是 mock 数据），只有最终结论是样例。

### 5.6 接了真实模型之后（实测）

用 DeepSeek `deepseek-v4-flash` 跑价投专家：**3 轮、3 次工具调用、约 5.3k tokens**，
schema 校验通过。

过程中暴露了一个真实问题并已修复：**只写"严格输出 JSON"是不够的**。
第一版提示词下模型返回了结构更丰富的 JSON（多了 `meta`/`metrics` 层），
`candidates[0]` 缺少 `code`，被校验器正确拦下。

修复方式：把 **完整的 JSON Schema 原文拼进提示词**，并明确三条要求——
只输出 JSON、required 字段一个不能少、不要新增顶层字段（补充说明写进 `notes`）。

这也说明校验器不是摆设：**模型的"差不多对"必须被挡在写库之前。**

## 6. 与编排的关系（当前边界）

v0.1 里，编辑器保存的配置用于：**持久化 + 试运行**。
内置的 5 个 Agent 仍由代码实现（确定性规则，可回测、可审计）。

自定义智能体接入日常流程（`POST /api/runs`）属于 v0.2，需要补两件事：

1. `TaskPlan` 生成时读取 `enabled=true` 的自定义 Agent
2. `ConfigDrivenAgent` 实现 `BaseAgent` 接口，接入 registry

这两步不改变契约，只增加一个 Agent 实现，风险可控。

## 7. 提示词与配置版本历史

每行「版本」按钮打开历史抽屉，可对比差异、一键回滚。

### 6.1 三条规则

| 规则 | 原因 |
|---|---|
| **整份配置进快照**（角色 + 工作流 + 工具 + 输出格式 + 启用） | 只存 prompt 会漏掉工作流/工具的改动，而它们同样改变行为 |
| **内容没变不建版本** | 避免"保存了但没改"把版本列表刷满 |
| **回滚生成新版本，不覆写历史** | 任何时刻历史都站得住，误操作还能再滚回来 |

### 6.2 API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/agents/{id}/versions` | 版本列表（倒序，含完整 payload） |
| GET | `/api/agents/{id}/versions/{version}` | 单个版本详情 |
| GET | `/api/agents/{id}/versions/{version}/diff` | 与**当前配置**对比；加 `?against=N` 与指定版本对比 |
| POST | `/api/agents/{id}/versions/{version}/restore` | 回滚（生成新版本） |

`diff` 返回字段级差异，只包含真正变化的字段：

```json
{
  "before_label": "v1",
  "after_label": "当前配置",
  "changes": [
    { "field": "role", "label": "角色描述", "before": "旧角色", "after": "新角色" },
    { "field": "tools", "label": "可用工具", "before": ["market.quotes"], "after": ["market.quotes", "calc.score"] }
  ]
}
```

### 6.3 版本号从哪来

- 新建智能体 → `v1`（note: 创建）
- 每次有效修改 → `vN+1`（note: 编辑）
- 回滚 → `vN+1`（note: 回滚至 vX）
- 内置智能体首次启动 → `v1`（note: 初始版本），由 `ensure_versions()` 补齐

## 9. 角色字段的三层拆分（2026-11-13）

早期只有「角色描述」一个 `role` 字段，结果一个 600 字的智能体全塞在里面：
画像权重、输出模板、人格设定混在一起，改一行要在长文本里翻。

现在拆成 **三个独立编辑区**，各自的职责和长度上限都不一样：

| 字段 | 界面名 | 放什么 | 上限 | 进提示词的位置 |
|---|---|---|---|---|
| `role` | 角色定位 | 你是谁、管什么、不管什么（1–3 句） | 2000 | 最开头 |
| `profile` | 角色画像 | 性格权重、信念、偏好、忌讳 | 4000 | `## 角色画像` |
| `output_spec` | 输出规范（报告模板） | 报告结构、必含段落、措辞要求 | 8000 | `## 输出规范` |
| `output_format` | 输出格式 | 机器可校验的类型（text / markdown_table / json_schema） | — | `## 输出要求` |

**为什么 `output_spec` 不合并进 `output_format`：**
一个是给模型看的自然语言模板，一个是给程序校验的类型与 schema。
把模板塞进 `json_schema.schema` 会破坏校验；把校验规则写进模板又无法被程序执行。

**空块不拼接：** `profile` 或 `output_spec` 为空时，对应的 `##` 标题整体不出现，
避免模型看到空标题后自己脑补内容。

**历史数据迁移**：`backend/scripts/migrate_split_profile.py` 会把旧的单段 `role`
按 `Profile：` / `Output Format` 标记拆成三段，可重复执行（已拆过的不再动），
支持 `--dry-run` 先看效果。

## 10. 两个容易踩的坑（已修）

### 10.1 老前端保存会清空新字段

新增 `profile` / `output_spec` 后，**还在跑旧 bundle 的浏览器**保存时不会带上这两个字段。
如果后端按 Pydantic 默认值 `""` 处理，等于每次保存都把它们清空——真实发生过一次，
靠版本历史 v1 的原始文本才恢复回来。

修法：两个字段声明为 `str | None = None`，`update` 时 `if body.profile is not None`
才覆盖。**"没传" 和 "传了空字符串" 是两件事**，前者是兼容，后者是用户主动清空。

### 10.2 index.html 不能缓存

它引用带 hash 的 bundle；一旦被浏览器缓存住，用户永远加载到旧前端，
表现为"新功能看不到"。所以 `index.html` 响应固定带：

```
Cache-Control: no-cache, no-store, must-revalidate
```

`/assets/*` 保持默认缓存（文件名带 hash，内容变了文件名就变）。

### 10.3 工作流步骤名不手填

步骤的「第 N 步」是**位置标签**，不是字段：

- 界面上只读显示 `第 {index+1} 步`，`name` 存在 hidden 字段里
- 增删步骤后按当前顺序自动重排（`renumberSteps`）
- 只重排"占位式"名字（空、`第 N 步`、`第一步`）；内置 Agent 的语义化名字（如"取标的池"）保留
- 后端 `_steps()` 兜底：`name` 为空时自动补 `第 N 步`，接口调用也不会出现空步名
